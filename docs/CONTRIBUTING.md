# 협업 규칙

[처음부터 따라 하기](../reference/B2-2-scenarios.md) · [내 역할](../README.md#tasks)

팀원 모두 읽고, 2차 PR에서 각자 담당한 규칙을 팀 합의에 맞게 보완합니다.

## 저장소 준비 · 관리자

- 팀원 4명의 접근 권한을 확인합니다.
- main에 PR 필수·타인 승인 1개 이상·우회 제한을 설정하고 force push를 금지합니다.
- 준비본도 Issue·PR·타인 리뷰를 거쳐 반영합니다.
- 실제 적용 화면을 증빙으로 남깁니다. 기능 제공 여부는 저장소 공개 범위·요금제에 따라 확인합니다.

[GitHub 보호 브랜치 안내](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)를 참고합니다.
설정을 확인하지 않았다면 제출 문서에 완료로 표시하지 않습니다.

## 브랜치 규칙 · A 담당

- `main`: 실습 완료 후 `src/`의 모든 함수가 정상 결과를 내는 상태를 목표로 합니다. 현재 준비본은 오류 수정 실습용이므로 의도적인 오류 4개를 포함합니다.
- 각 feature에서 담당 함수를 수정·검증한 후 병합합니다. 첫 PR 4개가 모두 병합된 다음부터 전체 함수의 정상 실행을 병합 기준으로 유지합니다.
- 따라서 준비본을 포함해 main이 항상 정상이라는 원문의 운영 기준까지 충족했다고 표기하지 않습니다.
- `feature/<역할>-<작업>`: Issue 하나에 대응하는 작은 작업. 예: `feature/a-upper`.
- 브랜치는 커밋을 가리키는 이름입니다. 각자 브랜치를 만들어 서로의 작업을 분리합니다.
- main에는 직접 push하지 않고 PR로만 병합합니다.
- 이번 실습은 **Create a merge commit**을 사용합니다. 공유 브랜치의 히스토리는 다시 쓰지 않습니다.

GitHub Flow는 작은 작업을 짧은 브랜치에서 완성하고 검토하기에 적합합니다.
실행 가능한 main을 유지하며, Issue와 PR로 변경 이유와 결정을 추적할 수 있어 선택했습니다.

## 커밋 규칙 · B 담당

- 형식: `feat: 대상과 효과`, `fix: 대상과 효과`, `docs: 대상과 효과`.
- 좋은 예: `feat: add uppercase conversion`, `docs: record soft reset exercise`.
- `update`, `fix`, `wip`, `final`, `bug fix`처럼 대상·효과가 불분명한 메시지는 쓰지 않습니다.
- 필요한 파일만 `git add`하고 `git diff --cached`로 확인합니다.
- amend/reset은 원격에 공개하지 않은 본인 feature 커밋에만 사용합니다.

## PR 규칙 · C 담당

- 모든 작업은 Issue로 만들고 PR 본문에 `Closes #실제번호`를 적습니다.
- 템플릿의 What(변경), Why(이유), How(실행 명령·예상 결과·실제 출력)를 채웁니다.
- 실습 PR은 해당 기록 문서와 전후 커밋을 연결합니다.
- 최종 변경에 대한 타인 승인 1개 이상, 작성자 응답, 충돌 없음, 실행 확인 후 병합합니다.
- 전원 PR 2개 이상 병합, 본인 PR에서 리뷰 수정 반영 1회 이상을 남깁니다.
- 리뷰·커밋 URL은 보관했다가 제출 정리 담당자에게 전달합니다.

## 리뷰 규칙 · D 담당

- 본인 PR을 제외한 PR 2개 이상에 파일·함수를 근거로 실질 코멘트를 남깁니다.
- 예: “`count_characters`가 중간 공백도 세는지 docstring과 실행 결과에 명시해 주세요.”
- 예: “`count_words`에 공백만 입력했을 때 0이 나오는지도 확인해 주세요.”
- 작성자는 답글과 수정 커밋으로 응답합니다. 반영하지 않는 의견은 이유를 설명합니다.
- `LGTM`만으로 끝내지 않습니다. 리뷰 코멘트와 Approve는 별개이므로 최종 승인도 확인합니다.

## 충돌 대응 · D 담당

1. 브랜치 작성자가 상대에게 파일·기준 커밋·변경 의도를 공유합니다.
2. `git status`와 `git diff`로 양쪽 내용을 보고 최종 내용을 합의합니다.
3. 양쪽 의도를 반영하고 마커를 제거합니다.
4. 파일을 `git add` 또는 `git rm`으로 정리하고 미해결 충돌이 없는지 확인합니다.
5. 사용 예시를 실행한 뒤 merge 커밋을 만들고 [충돌 기록](conflict-resolution.md)에 남깁니다.

깨끗한 작업 트리에서 시작한 merge를 취소하려면 `git merge --abort`를 사용합니다.
같은 문서의 다른 사람 기록을 지우지 않습니다.

## 마지막에 함께 설명해 보기

- 긴급 수정: 최신 main에서 작은 브랜치 → Issue·수정·실행 → PR·신속한 타인 승인 → 병합.
- 이미 공개한 나쁜 커밋 메시지: PR 설명을 보완하고 후속 커밋부터 규칙 적용. 강제 push로 바꾸지 않기.
- 반복 충돌: 작업 범위·파일 분담·동기화 시점을 점검하고 PR 크기 줄이기.
