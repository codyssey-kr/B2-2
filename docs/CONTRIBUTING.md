# 협업 규칙

팀원은 아래 규칙을 기준으로 작업하며, 규칙을 변경할 때는 PR에서 논의하고 합의합니다.

## 저장소 관리

- 팀원에게 작업에 필요한 접근 권한을 부여합니다.
- `main`에 브랜치 보호를 설정해 PR과 작성자 외 1명 이상의 승인을 요구합니다.
- `main`의 강제 push와 보호 규칙 우회를 제한합니다.

## 브랜치 규칙

- `main`은 항상 정상 실행 및 배포 가능한 상태로 유지합니다.
- 작업은 최신 `main`에서 새 브랜치를 만들어 시작합니다.
- 브랜치는 하나의 목적을 가진 작은 작업 단위로 나눕니다.
- 이름은 `feature/<작업>`, `fix/<작업>`, `docs/<작업>`처럼 목적을 드러냅니다.
- `main`에는 직접 push하지 않고 PR로만 병합합니다.
- 병합 방식은 팀에서 합의한 방식을 따르며, 병합이 끝난 작업 브랜치는 정리합니다.
- 다른 사람이 사용하는 공유 브랜치의 커밋 이력을 다시 쓰지 않습니다.

## 커밋 규칙

- 하나의 커밋에는 하나의 논리적인 변경을 담습니다.
- 비밀키, 비밀번호, 개인 설정, 불필요한 생성 파일은 커밋하지 않습니다.

## PR 규칙

- 작업 전에 Issue로 목적과 범위를 결정하고, PR에서 관련 Issue를 연결합니다.
- PR 본문에는 What(변경 내용), Why(변경 이유), How(구현 방법과 검증 결과)를 작성합니다.
- 관련 없는 변경은 별도 PR로 나누고, 작업 중인 PR은 Draft로 표시합니다.
- 리뷰 의견을 처리하고, 충돌을 해결하고, 필요한 실행 확인과 검사를 마친 뒤 병합합니다.
- 최종 변경에 대해 작성자 외 1명 이상의 승인을 받습니다.

## 리뷰 규칙

- 변경 목적, 동작의 정확성, 가독성, 기존 기능에 미치는 영향을 확인합니다.
- 반드시 수정해야 하는 사항과 선택적인 제안을 구분합니다.
- 작성자는 의견에 답변하고, 반영하지 않는 경우에는 이유를 설명합니다.
- 승인할 때는 확인한 내용과 검증 범위를 간단히 남깁니다.

## 문제 대응

- 문제를 공유할 때는 발생 상황, 재현 절차, 예상 결과, 실제 결과를 함께 적습니다.
