# B2-2 체크리스트 모범 답안

[원문 체크리스트](B2-2-checklist.md) · [미션 원문](B2-2.md) · [팀 실행 안내](B2-2-scenarios.md)

이 문서는 체크리스트의 필수 21개 항목에 대응하는 **설명·발표·회고용 답안 예시**입니다. 보너스 1개 항목은 제외로 표시합니다. 수행 완료 보고서가 아닙니다.
현재 로컬 준비본에는 정상 공통 함수와 의도적인 오류가 있는 팀원별 함수 4개, 협업 규칙·기록 양식이 있습니다. 실제 팀 PR·리뷰·원격 설정은 이 문서 작성 과정에서 검증하지 않았습니다.

- 항목 1의 답안은 **실습을 완료했을 때 설명할 수 있는 예시**입니다. 실제 수행 내용으로 고치고 증빙을 채운 후 사용합니다.
- 항목 2~4는 현재 팀 계획을 바탕으로 한 방법·이유·상황 대응 답안입니다. 실제 결정이 달랐다면 그 이유와 사례로 수정합니다.
- A~D는 역할, A1~D2는 작업 이름입니다. 실제 이름·GitHub ID·Issue 번호·PR URL·SHA로 바꿉니다.
- 원문의 “비자영 충돌”은 미션 본문의 **비자명 충돌**을 가리키는 것으로 해석했습니다. 아래 질문은 원문 그대로 유지했습니다.
- 이 답안이 있다는 이유로 원문 체크박스나 제출 문서의 상태를 완료로 바꾸지 않습니다.

## 항목 1. 수행 결과와 증빙

### 1-1. 팀 저장소와 참여 권한

**체크리스트:** (옵션 A/B) 저장소가 팀 단위로 1개이며, 팀원이 협업 가능한 권한으로 참여했는가?

**모범 답안 — 완료 후 설명 예시**

우리 팀은 A·B·C·D 네 명이 하나의 팀 저장소를 사용합니다. 각 팀원은 자기 계정으로 저장소에 접근하고 feature 브랜치를 push하고 PR을 만들 수 있습니다. 개인별로 따로 제출하지 않고 모든 기여를 같은 저장소에 모았습니다. 조직 저장소라면 조직의 팀·역할로, 개인 저장소라면 Collaborator 초대로 권한을 부여했습니다.

**실제 증빙:** `저장소 URL`, `선택한 옵션 A 또는 B`, `팀원 4명의 GitHub ID`, `참여 권한 확인 자료`를 [SUBMISSION.md](../SUBMISSION.md)에 적습니다. 이 저장소의 로컬 origin은 `https://github.com/codyssey-kr/B2-2`이지만, 그 사실만으로 네 사람의 권한까지 확인된 것은 아닙니다.

### 1-2. main 보호와 PR 병합

**체크리스트:** main 브랜치에 Branch Protection이 설정되어 있고, 직접 push 없이 PR로만 병합되었는가?

**모범 답안 — 완료 후 설명 예시**

main에는 PR을 통해서만 변경이 들어가도록 보호 규칙을 적용하고, 작성자 외 최소 한 명의 승인을 요구했습니다. 관리자 등의 우회 허용도 제한했습니다. 팀원은 feature 브랜치에 push하고 리뷰를 받은 뒤 PR을 병합했습니다. 설정 화면뿐 아니라 실제 병합된 PR과 main의 히스토리도 확인했습니다.

**실제 증빙:** `main 보호 설정 화면`, `승인 기록이 있는 병합 PR URL`, `git log --oneline --graph --all` 결과를 남깁니다. 보호 설정만으로 과거의 직접 push가 없었다고 단정하지 않습니다. 보호 규칙의 관리자 적용 여부는 별도로 설정할 수 있습니다. [GitHub 보호 브랜치 문서](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

### 1-3. Issue와 PR 연결

**체크리스트:** 각 PR이 이슈와 연동되어 있으며(예: Closes #n), 추적 가능한가?

**모범 답안 — 완료 후 설명 예시**

구현 전에 작업 목적·담당자·완료 기준을 Issue로 만들었습니다. PR 본문에는 그 Issue의 실제 번호를 `Closes #번호`로 적어 변경 이유와 구현 결과를 오갈 수 있게 했습니다. 예를 들어 대문자 변환 함수 Issue에는 `src/1_upper.py` 구현 PR을 연결했습니다. README의 A1·B1 같은 표시는 역할별 작업 이름이고 실제 Issue 번호와는 구분했습니다.

**실제 증빙:** 팀원별 `Issue URL ↔ PR URL`을 제출 문서에 적고 연결 상태를 확인합니다. `Closes`에 의한 자동 종료는 PR의 대상이 저장소의 기본 브랜치이고 그 브랜치에 병합되는 조건에서 적용됩니다. 이 팀에서는 main이 기본 브랜치인지 확인합니다. [GitHub Issue·PR 연결 문서](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

### 1-4. 팀원별 병합 PR 2개

**체크리스트:** 팀원별로 PR 2개 이상이 병합되어 있고, 팀원별 PR 링크를 SUBMISSION.md 에서 확인할 수 있는가?

**모범 답안 — 완료 후 설명 예시**

각 팀원이 함수 구현 PR 하나와 Git 실습·기록 PR 하나를 작성해 병합했습니다. A는 대문자 변환과 소개 문장·amend, B는 소문자 변환과 소개 충돌·reset, C는 글자 수와 실행 예시·revert, D는 단어 수와 예시 충돌·stash를 맡았습니다. 따라서 네 사람 모두 본인이 작성한 병합 PR이 두 개 이상입니다.

**실제 증빙:** [SUBMISSION.md](../SUBMISSION.md)의 A~D 항목에 각자 `첫 PR URL`과 `두 번째 PR URL`을 채웁니다. PR 작성자와 **Merged 상태**를 확인합니다. 팀 전체가 8개여도 특정 팀원이 1개만 작성했다면 이 항목은 전원 충족이 아닙니다. 준비본을 한 사람이 일괄 작성한 기록으로 다른 사람의 PR을 대신하지 않습니다.

### 1-5. 타인 리뷰와 본인 리뷰 반영

**체크리스트:** 팀원별로 리뷰 2개 이상이 존재하고, 각 팀원이 최소 1회는 본인 PR에서 리뷰를 반영했는가?

**모범 답안 — 완료 후 설명 예시**

첫 PR은 A→D1, B→A1, C→B1, D→C1을 리뷰하고, 두 번째 PR은 A→B2, B→C2, C→D2, D→A2를 리뷰하도록 배정했습니다. 각자 다른 사람의 PR 두 개에 구체적인 코멘트를 남겼습니다. 작성자는 답글로 응답하고, 본인 PR에서는 최소 한 번 코드·예시·설명을 실제로 수정해 의견을 반영했습니다.

예를 들어 C의 `count_characters` 리뷰에서 “중간 공백도 글자 수에 포함되는지 예시를 보완해 주세요”라는 의견을 받으면, C는 docstring과 실행 결과를 보완하고 해당 커밋을 답글에 연결합니다. 이 대화는 설명용 예시이며 실제 수행 기록으로 간주하지 않습니다.

**실제 증빙:** 팀원마다 `본인이 작성한 타인 리뷰 URL 2개`, `본인 PR의 피드백 스레드`, `반영 커밋 URL`을 남깁니다. Approve만 있는 기록과 실질 코멘트가 있는 리뷰를 구분합니다.

### 1-6. 충돌 2회와 비자명 충돌

**체크리스트:** 충돌 해결 기록이 최소 2회 존재하며, 그 중 1회는 비자영 충돌 기준을 충족하는가?

**모범 답안 — 완료 후 설명 예시**

첫 번째는 A와 B가 같은 기준 커밋에서 README의 소개 문장 한 줄을 각각 함수 구현 중심과 PR·리뷰 중심으로 바꿔 충돌시켰습니다. A2 병합 후 B가 main을 합치고 두 목적을 담은 문장으로 해결했습니다. 두 번째는 C와 D가 README의 같은 실행 명령을 각각 Python 입력과 Git 입력으로 바꿔 충돌시켰습니다. C2 병합 후 D가 main을 합치고 두 명령과 각각의 예상 출력을 모두 보존했습니다.

두 경우 모두 같은 파일의 **같은 hunk를 서로 다르게 수정**한 충돌입니다. 미션이 제시한 비자명 충돌 조건을 만족하며, 파일 삭제·이동 충돌을 추가로 만들 필요는 없습니다.

**실제 증빙:** [충돌 기록](../docs/conflict-resolution.md)에 `기준 SHA`, `양쪽 브랜치·커밋`, `실제 마커`, `해결 이유`, `해결 커밋·PR URL`을 두 건 남깁니다. 시나리오가 작성되어 있는 것만으로 수행 완료가 되지는 않습니다.

### 1-7. Git 트러블슈팅 4종과 참여

**체크리스트:** 트러블슈팅 4종(amend/reset/revert/stash)이 모두 수행되었고, 팀원별로 최소 1개 시나리오 기록에 참여했는가?

**모범 답안 — 완료 후 설명 예시**

네 사람이 한 가지씩 실습하고 본인이 수행·기록한 부분에 이름을 남겼습니다.

| 담당 | 실습 | 완료 후 확인할 결과 |
| --- | --- | --- |
| A | `git commit --amend` | 미공개 최근 커밋의 메시지·SHA는 바뀌고 파일 내용을 나타내는 tree SHA는 같음 |
| B | `git reset --soft HEAD~1` | HEAD가 부모 커밋으로 이동하고 변경이 staged 상태로 유지되어 재커밋 가능 |
| C | `git revert` | 원격에 공개한 README 임시 안내 커밋과 이를 취소하는 새 커밋이 모두 남음 |
| D | `git stash` / `git stash pop` | 미완성 변경을 보관하고 브랜치를 전환한 뒤 원래 변경을 복원 |

**실제 증빙:** [트러블슈팅 기록](../docs/troubleshooting-log.md)의 T1~T4에 이름·역할·명령·전후 결과·커밋 링크를 채웁니다. C는 원본 커밋이 원격에 있었음을, D는 보관 전후 diff가 같은지를 확인합니다. `stash pop`은 충돌 없이 성공한 경우 항목을 제거하며, 충돌한 경우에는 stash가 남을 수 있습니다. [Git stash 문서](https://git-scm.com/docs/git-stash)

### 1-8. 필수 협업 문서 3종

**체크리스트:** docs/CONTRIBUTING.md, docs/conflict-resolution.md, docs/troubleshooting-log.md 가 존재하고 템플릿 수준의 구조를 갖추었는가?

**모범 답안 — 완료 후 설명 예시**

`docs/CONTRIBUTING.md`에는 브랜치·커밋·PR·리뷰·충돌 대응 규칙을 정리했습니다. `docs/conflict-resolution.md`에는 참여자, 상황, 충돌 내용, 해결 과정·이유, 결과, 배운 점을 기록했습니다. `docs/troubleshooting-log.md`에는 네 실습의 참여자, 상황, 실제 절차, 전후 결과와 주의점을 기록했습니다.

**실제 증빙:** [협업 규칙](../docs/CONTRIBUTING.md), [충돌 기록](../docs/conflict-resolution.md), [트러블슈팅 기록](../docs/troubleshooting-log.md)을 연결합니다. 현재 세 파일은 존재하지만 기록 문서는 미수행 양식입니다. 파일 존재·양식 준비와 실제 내용 작성 완료는 별도로 판단합니다.

## 항목 2. 협업 방법 설명

### 2-1. 작업 단위로 브랜치 나누기

**체크리스트:** 브랜치 전략을 "작업 단위"로 나누는 기준을 어떻게 정했는지 설명할 수 있는가?

**모범 답안**

Issue 하나의 목적과 완료 기준을 설명할 수 있는 범위를 작업 단위로 정합니다. 함수 하나의 구현과 docstring 예시는 함께 검토할 수 있으므로 같은 PR에 넣습니다. 반면 함수 구현과 Git 실습 기록은 목적이 달라 별도 브랜치·PR로 나눕니다. 단순히 팀원마다 장기간 쓰는 브랜치를 하나씩 두는 방식은 사용하지 않습니다.

예를 들어 A는 `feature/a-upper`에서 대문자 변환을 구현하고, 병합 후에는 별도의 `feature/a-intro`에서 README 소개와 amend 실습을 진행합니다. 브랜치는 커밋을 가리키는 이름이므로 같은 main에서 분기해도 각자의 작업 커밋을 독립적으로 쌓을 수 있습니다.

**연결 자료:** [역할과 실행 예시](../README.md#tasks), [브랜치 생성 절차](B2-2-scenarios.md#first-task), [협업 규칙](../docs/CONTRIBUTING.md).

### 2-2. What·Why·How와 템플릿

**체크리스트:** PR 본문에 What/Why/How와 이슈 연동 정보를 일관되게 남기기 위해 어떤 규칙/도구(템플릿 등)를 썼는지 설명할 수 있는가?

**모범 답안**

[PR 템플릿](../.github/pull_request_template.md)에 연결 Issue, What, Why, How를 고정했습니다. 작성자가 PR을 만들 때 채우고 리뷰어가 누락 여부를 확인합니다. Issue에도 [작업 템플릿](../.github/ISSUE_TEMPLATE/task.md)을 사용해 담당자·목적·완료 기준을 먼저 정합니다.

A의 PR을 예로 들면 What은 “공통 공백 정리 후 대문자를 반환하는 함수 구현”, Why는 “팀원별 유틸 함수 기여와 코드 재사용 연습”, How는 “`python3 src/1_upper.py` 실행, 예상 `HELLO TEAM`, 실제 출력 기록”입니다. 빈 입력·한글 입력 결과도 확인합니다. `Closes #실제번호`를 넣고 번호를 팀 작업 이름 A1로 대체하지 않습니다.

**실제 사례를 설명할 때:** 템플릿 파일만 보여 주지 말고, 해당 항목을 채운 본인 PR URL을 함께 제시합니다.

### 2-3. 실질적인 리뷰의 최소 품질

**체크리스트:** 리뷰 코멘트가 "LGTM"에 그치지 않도록 팀에서 적용한 최소 품질 기준과 운영 방법을 설명할 수 있는가?

**모범 답안**

모든 PR에 파일·함수·라인을 근거로 한 질문, 개선 제안 또는 리스크 설명을 하나 이상 남깁니다. 작성자도 답글이나 수정으로 응답해야 합니다. 리뷰 코멘트를 작성한 것과 최종 Approve 상태를 구분하고, 수정된 내용까지 확인한 뒤 승인합니다.

예를 들어 “좋아요” 대신 “`count_words`에 공백만 입력했을 때도 0이 되는지 실행 예시를 추가해 주세요”라고 제안합니다. 작성자는 확인한 입력과 결과를 docstring이나 PR 본문에 보완하고 답글로 연결합니다. 버그가 없으면 설명·사용 예시의 실제 보완점을 논의하며, 리뷰 실적을 위해 일부러 잘못된 코드를 넣지 않습니다.

**연결 자료:** [협업 규칙](../docs/CONTRIBUTING.md)의 리뷰 규칙과 실제 리뷰 스레드·반영 커밋.

### 2-4. 충돌 발생 후 대응 흐름

**체크리스트:** 충돌 발생 시, 팀이 어떤 흐름(공유→해결→기록)으로 대응했는지 설명할 수 있는가?

**모범 답안**

충돌을 발견한 브랜치 작성자가 상대 팀원에게 대상 파일·기준 커밋·각자의 변경 의도를 공유합니다. `git status`와 `git diff`로 충돌 부분을 확인한 다음, 한쪽을 무조건 선택하지 않고 보존할 요구사항을 합의합니다. 수정·마커 제거 후 `git add`하고 `git diff --name-only --diff-filter=U`에 남은 파일이 없는지 확인합니다.

예를 들어 B는 A의 함수 구현 소개와 자신의 리뷰 소개를 함께 담은 문장으로 합칩니다. 관련 사용 예시와 문서 링크를 확인하고 merge 커밋을 만든 뒤, 해결 이유와 커밋·PR을 [충돌 기록](../docs/conflict-resolution.md)에 남겨 상대가 검토하도록 합니다.

**설명 순서:** 발견 → 상대와 공유 → 양쪽 의도 확인 → 해결·검증 → 기록·리뷰.

### 2-5. 재현 가능한 트러블슈팅 로그

**체크리스트:** 트러블슈팅 로그를 "재현 가능"하게 만들기 위해 어떤 항목(상황/절차/결과/주의점)은 고정했는지 설명할 수 있는가?

**모범 답안**

누가 어떤 브랜치·커밋에서 무엇을 하다가 문제가 생겼는지부터 적습니다. 실행한 명령을 순서대로 남기고 실제 출력·전후 SHA·staged 상태·작업 파일 변경을 함께 적습니다. 마지막에는 해결 결과, 선택 이유, 원격 공개 여부와 협업에 미치는 주의점을 씁니다.

`reset --soft`라면 “커밋을 취소했다”로 끝내지 않습니다. 취소 전 HEAD와 부모 SHA, 사용한 명령, 취소 후 HEAD, `git diff --cached`, 재커밋 결과를 남겨 변경이 유지되었는지 확인할 수 있게 합니다. 예상 결과와 실제 출력은 구분하며 재현하지 않은 내용을 완료로 쓰지 않습니다.

**연결 자료:** [트러블슈팅 기록 양식](../docs/troubleshooting-log.md).

## 항목 3. 이유와 원리 설명

### 3-1. main을 실행 가능한 상태로 유지하는 이유

**체크리스트:** GitHub Flow에서 main을 "항상 배포 가능 상태"로 유지해야 하는 이유를 설명할 수 있는가?

**모범 답안**

main은 팀원이 새 작업을 시작하고 결과물을 확인하는 공통 기준입니다. main이 깨져 있으면 다른 사람이 자기 코드와 공통 코드 중 무엇 때문에 실패하는지 구분하기 어렵고 작업 전체가 지연됩니다. 그래서 변경을 작은 PR로 검토하고, 병합 전에 공통 함수와 구현된 함수의 사용 예시를 직접 실행합니다.

이 프로젝트에는 별도 웹 서비스 배포가 없으므로 “배포 가능”은 저장소를 받아 안내된 명령으로 구현된 기능을 실행할 수 있다는 뜻으로 정합니다. **현재 준비본의 `src/`에는 오류 수정 실습을 위한 의도적인 오류 4개가 있습니다.** 각 feature에서 담당 함수를 고쳐 첫 PR 4개를 병합한 뒤 전체 기능의 정상 상태를 유지합니다. 최종 제출 시에는 네 함수 모두 예상 결과가 나와야 합니다. 준비본 단계까지 main이 항상 정상이라는 원문의 운영 기준을 충족한 것으로 설명하지 않습니다.

**완료 후 제시할 예:** `python3 src/3_length.py`의 실제 출력이 `10`이며, 빈 입력은 `0`임을 확인한 기록.

### 3-2. 직접 push 대신 PR과 승인

**체크리스트:** main에 직접 push하지 않고 PR + 승인으로 병합하는 이유(품질/책임/추적성)를 설명할 수 있는가?

**모범 답안**

PR은 변경을 main에 넣기 전에 다른 사람이 검토할 기회를 만듭니다. 리뷰어는 기능뿐 아니라 사용 예시·영향 범위·변경 이유도 확인하므로 놓친 문제를 찾을 수 있습니다. 누가 작성하고 누가 어떤 의견을 남겼으며 왜 병합했는지가 남아 추적과 인수인계에도 도움이 됩니다.

승인은 책임을 한 사람에게 넘기는 절차가 아니라 최종 변경을 공동으로 확인하는 과정입니다. 작성자는 실행 결과를 제시하고, 리뷰어는 반영 내용을 확인합니다. main 보호 규칙은 이 절차를 누락한 병합을 막는 수단이며 실제 설정·적용을 확인해야 합니다.

**연결 자료:** [협업 규칙](../docs/CONTRIBUTING.md), 승인·수정 이력이 남은 실제 PR.

### 3-3. Issue·PR 연동의 가치

**체크리스트:** 이슈-PR 연동을 하는 이유(추적성/커뮤니케이션/자동화)를 설명할 수 있는가?

**모범 답안**

Issue에는 해결하려는 문제·담당자·완료 기준을, PR에는 실제 변경과 검증 결과를 둡니다. 둘을 연결하면 이 코드가 왜 필요한지와 어떤 작업이 어디까지 진행되었는지를 쉽게 찾을 수 있습니다. 후속 담당자도 Issue에서 PR·리뷰·커밋으로 이동하며 결정 이유를 확인할 수 있습니다.

닫기 키워드는 기본 브랜치 대상 PR이 병합될 때 관련 Issue를 자동 종료하는 데에도 쓰입니다. 다만 `Closes`를 적었다는 사실만으로 구현이나 검증이 끝나는 것은 아니므로 리뷰어가 Issue의 완료 기준을 실제로 확인합니다. [GitHub Issue·PR 연결 문서](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

### 3-4. 공개 커밋 취소에 revert를 쓰는 이유

**체크리스트:** 원격에 push된 커밋을 되돌릴 때 reset 대신 revert를 선택해야 하는 이유를 설명할 수 있는가?

**모범 답안**

`reset`은 현재 브랜치의 위치를 이전 커밋으로 옮깁니다. 이미 원격에 공개한 이력을 이 방식으로 되돌려 덮어쓰면 다른 사람이 받아 둔 이력과 달라질 수 있습니다. `revert`는 대상 변경을 취소하는 새 커밋을 추가하므로 기존 커밋과 취소 이유를 함께 남기며 협업 이력을 유지할 수 있습니다.

따라서 B의 `reset --soft`는 미공개 로컬 커밋에만 적용하고, C가 원격에 공개한 README 임시 안내는 `revert`로 취소합니다. 취소 커밋도 실행·검토 후 일반 push와 PR 절차로 반영합니다. revert 도중에도 후속 변경과 충돌할 수 있으므로 결과 확인은 필요합니다. [Git reset 문서](https://git-scm.com/docs/git-reset), [Git revert 문서](https://git-scm.com/docs/git-revert)

### 3-5. 충돌 마커와 해결 기준

**체크리스트:** 충돌 마커(\<\<\<\<\<\<\<, =======, \>\>\>\>\>\>\>)의 의미와, 비자영 충돌을 해결할 때 고려한 의사결정 기준을 설명할 수 있는가?

**모범 답안**

이번 실습처럼 B 또는 D의 feature 브랜치에서 `git merge origin/main`을 실행한 경우, `<<<<<<< HEAD` 아래부터 `=======` 위까지가 현재 브랜치의 내용이고, `=======` 아래부터 `>>>>>>> origin/main` 위까지가 합쳐지는 main의 내용입니다. Git이 자동으로 하나를 선택할 수 없어 양쪽 내용을 보여 주는 것입니다. 이것을 모든 rebase 상황에서도 단순히 “내 것/남의 것”으로 외우지는 않습니다.

해결 기준은 작성자가 누구인지가 아니라 두 변경이 지키려던 요구사항입니다. 소개 문장은 구현과 리뷰라는 두 목적을 담고, 실행 예시는 Python 입력과 Git 입력 및 각 예상 출력을 함께 남깁니다. 마커만 지우는 것으로 끝내지 않고 중복·누락·실행 결과를 확인합니다.

**실제 증빙:** [충돌 기록](../docs/conflict-resolution.md)의 두 변경 의도, 합의 이유, 최종 diff와 해결 커밋.

## 항목 4. 상황 대응

### 4-1. 긴급 핫픽스 처리

**체크리스트:** 만약 main에 긴급 핫픽스가 필요하다면, GitHub Flow에서 어떤 순서로 처리할지(브랜치/PR/리뷰/배포) 설명할 수 있는가?

**모범 답안**

최신 main에서 긴급 수정용 feature 브랜치를 만들고, 문제 증상과 기대 동작을 Issue에 적습니다. 예를 들어 단어 수 함수가 빈 문자열을 1로 센다면 빈 입력으로 재현한 뒤 최소 범위로 고칩니다. 정상 입력과 빈 입력을 직접 실행해 수정 전후 결과를 PR에 남깁니다.

리뷰어에게 긴급도를 알리고 검토를 빠르게 진행하되 PR과 타인 승인 절차는 유지합니다. 승인 후 main에 병합하고 최신 main에서 다시 실행합니다. 이 프로젝트는 배포 서비스가 없으므로 병합된 코드의 재실행·공유가 마지막 단계입니다. 별도 운영 서비스가 있다면 이후 배포와 상태 확인까지 수행합니다.

**순서:** 최신 main → 짧은 브랜치·Issue → 재현·수정·실행 → PR·승인 → 병합 → 배포 또는 실행 확인. 긴급하다는 이유로 main 직접 push나 검증 생략을 기본 절차로 삼지 않습니다.

### 4-2. 의미 없는 커밋 메시지를 이미 push한 경우

**체크리스트:** 만약 팀원이 실수로 "의미없는 커밋 메시지"를 여러 개 push했다면, 협업 중단 없이 개선하는 방법을 설명할 수 있는가?

**모범 답안**

먼저 해당 브랜치를 누가 사용 중인지 확인하고, 이미 공유된 이력을 곧바로 amend·rebase·강제 push로 바꾸지 않습니다. PR 제목과 본문에 각 커밋이 무엇을 바꿨는지 보완하고, 이후의 실제 변경부터 구체적인 커밋 메시지를 사용합니다. 다른 팀원은 기존 커밋을 기준으로 계속 작업할 수 있습니다.

이 조치는 협업 중단을 줄이지만 **이미 공개된 나쁜 커밋 메시지가 사라지거나 미션의 금지 기준을 자동으로 충족하게 되는 것은 아닙니다.** 해당 이력을 사실대로 설명하고 평가 기준도 확인합니다. 메시지 수정을 위한 이력 재작성이 꼭 필요하면 영향받는 팀원 전원의 합의와 동기화 계획을 먼저 마련합니다. 이번 팀의 기본 규칙은 미공개 본인 커밋만 amend하고 공유 이력은 유지하는 것입니다.

**예방:** 커밋 전 대상·효과를 확인하고 `feat: add uppercase conversion`처럼 구체적으로 작성합니다.

### 4-3. 같은 영역에서 충돌이 반복되는 경우

**체크리스트:** 만약 충돌이 반복적으로 발생한다면(같은 파일/같은 영역), 원인 분석과 예방 방안을 제시할 수 있는가?

**모범 답안**

충돌이 반복된 파일·줄·시점과 각 브랜치의 작업 기간을 기록해 원인을 찾습니다. README 전체를 여러 사람이 동시에 편집했는지, 오래된 main에서 작업했는지, 하나의 PR에 서로 무관한 수정이 섞였는지 확인합니다.

이 팀에서는 함수별 파일을 분리하고, 사용 예시는 각 함수의 docstring에 작성합니다. README를 편집할 때는 담당 구간을 미리 공유하고 PR을 작게 유지합니다. 공통 함수 변경은 영향받는 팀원에게 먼저 알리고 사용 예시를 함께 확인합니다. 제출 링크 취합은 한 명이 맡아 동시 편집을 줄입니다.

의도적인 충돌 실습 중에는 충돌을 재현하기 위해 동일 기준에서 분기하고 합의한 시점까지 동기화를 기다립니다. 그 실습 조건을 일상적인 협업 규칙으로 오해하지 않습니다.

### 4-4. 보너스 항목 — 제외

**체크리스트:** (보너스 수행 시) 왜 리베이스가 히스토리를 깨끗하게 만들지만 협업에서는 위험할 수 있는지, 안전 수칙을 포함해 설명할 수 있는가?

**해당 없음:** 이번 팀 실습은 보너스 과제를 제외하므로 이 항목의 답안·수행·증빙은 준비하지 않습니다. 원문 체크리스트에서도 완료로 체크하지 않습니다.
